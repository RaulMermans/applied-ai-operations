# ADR-019: Durable execution, checkpoints, and replay protection

Status: accepted

## Context

Through Sprint 13 every Run, Approval, and retry counter lived in one process. A crash lost pending approvals and retry accounting, and nothing could tell whether an operation interrupted mid-flight had already affected the world. Sprint 14 makes execution durable without a second Runtime, a workflow platform, or new deployment infrastructure. The rule throughout: AAO may replay orchestration, but it never blindly replays an operation whose real-world outcome is ambiguous.

## Decision

- **AAO owns durability semantics in a new `@aao/durability` package.** It depends on `@aao/contracts`, `@aao/runtime`, `@aao/approval`, and `@aao/workflow-dsl`. `@aao/runtime` and `@aao/approval` never depend on it, and neither do Tool Runtime, Governance, or Authorization. Only the reference store touches the filesystem.
- **The Runtime remains the execution authority.** It exposes a generic durability port (`RuntimeOptions.durability`: `persistCheckpoint`, `beginAttempt`, `recordAttemptOutcome`, `isCancellationRequested`) and one general resume primitive, `resumeWorkflow`. It never loads or stores anything. `executeWorkflow`, `continueWaitingWorkflow`, and `resumeWorkflow` all enter the single `runLoop`. Every Node outcome is committed in one place: live, recovered, retried, or replayed. There is one patch application, one Node transition path, and one routing path. Without the port, Runtime behavior is unchanged.
- **Storage is replaceable.** `DurabilityStore` is a focused, storage-neutral port: create Run (atomic with checkpoint 0), write and read checkpoints, begin, replay-mark, and complete operations, list operations, request and read cancellation, and an Approval repository. It exposes no raw writes, queries, or key/value access.
- **The local filesystem is the first reference store.** It is local, single-host, single-writer, and restart-durable. It is not distributed, multi-worker, HA, or cloud persistence. Writes use validate → same-directory temp file → fsync → rename (or a hard link for create-if-absent) → directory fsync where supported. A Run is created by renaming a fully written staging directory into place. Paths are SHA-256 keys of validated identifiers. Store directories that are symlinks or non-directories fail closed. Every loaded record is schema-validated. Corruption fails closed and is never skipped. Failures are redacted to fixed codes. A native database was not introduced: nothing in the repository required one.
- **Single writer per Run.** One store instance serializes mutations per Run. Checkpoint sequences are create-if-absent. Operation, Approval, and cancellation updates are compare-and-set. One host refuses concurrent execution of the same Run (`DURABLE_RUN_BUSY`). There are no leases, election, or multi-process coordination.
- **Run identity and plan binding.** A Run manifest records `runId`, `workflowId`, `workflowVersion`, `planFingerprint`, `createdAt`, and the schema version. Lifecycle status is not duplicated; `RunRecord.status` inside the checkpoint stays authoritative. `planFingerprint` is SHA-256 over canonical JSON of the compiled plan, excluding only the human-facing `workflow.name` and `workflow.description`. Resume requires an identical workflow id, version, and fingerprint, otherwise `DURABILITY_PLAN_MISMATCH` and nothing executes. A changed plan under an unchanged version is still refused.
- **One canonical durable checkpoint.** `DurableCheckpoint` wraps the Runtime's `RuntimeExecutionSnapshot` and its `NodeExecutionRecord[]` history. It adds sequence, identity, plan fingerprint, and bounded terminal `failure` evidence. It also adds an optional `governanceFingerprint` captured at an approval wait, which is evidence, never authority. A snapshot is Runtime state representation; a checkpoint is proof of durable storage. Checkpoints are immutable, with strictly increasing, gap-free sequences per Run that are independent of timestamps. The early `CheckpointRecord` placeholder in `@aao/contracts` was **deleted**. It had no runtime usages, and the real checkpoint must wrap a Runtime type that `@aao/contracts` cannot depend on. Keeping it would have left two competing checkpoint contracts.
- **Checkpoints only at safe boundaries.** A checkpoint is written at initial `RUNNING` with the entry Node `READY`, after every accepted Node completion (next Node `READY`), at an approval wait, at each terminal boundary (`COMPLETED`, `FAILED` including preflight failure, `CANCELLED`), and at approval resolution. A snapshot never contains a `RUNNING` Node. `COMPLETED` and `WAITING_FOR_APPROVAL` are reported only after their checkpoint is durable. If any durability write fails, the Runtime stops with `DURABILITY_PERSISTENCE_FAILED` and reports the last durably persisted boundary with its status unchanged. It never invents a `FAILED` Run that storage does not hold.
- **Write-ahead operation intent.** Before every executor attempt the Runtime persists a `STARTED` operation (`op.s<step>.a<attempt>`), carrying Node, step, state revision, attempt, `maxAttempts`, and `recoveryReplayCount`. If that write fails, the executor is never invoked.
- **Outcome-first persistence.** After an attempt, the Runtime-validated outcome is persisted before the Runtime commits, retries, or routes anything. Only validated outcomes are persisted: success `{ statePatch?, output? }`, approval wait, or a classified failure with a Runtime-built message and bounded executor code. Raw executor responses, stacks, provider payloads, and secrets are never stored.
- **Accepted outcomes are recovered, not re-executed.** A recorded success or wait behind the latest checkpoint is fed through the same Reliability Controller and commit path without invoking the executor. Its patch applies exactly once and the state revision advances once.
- **Recovery safety is distinct from retry safety.** Retry safety means safe to retry after a known failure. Recovery safety means safe to replay after a crash left the outcome unknown. `RecoverySafetySchema` (`@aao/contracts`) and `NodeExecutor.recoverySafety?(node)` are trusted executor metadata, never derived from model, Agent, Tool, MCP, workflow-state, exception, or memory content. Absent means `unsafe`. Built-ins:
  - `final_output`: safe (pure).
  - Model Node: safe (no external side effect; a replay may cost tokens and differ).
  - Agent Node: safe (bounded Agents have no Tools, external actions, MCP, or delegation).
  - Approval Node: safe (deterministic exact-request ids and idempotent creation).
  - Tool Node: decided by the registered Tool.
- **Tool recovery rules.** A Tool is recovery-safe only when one of these holds:
  - Every permission class is `read_only`, and the Tool declares `retrySafety: "safe"` or `idempotency: "execution_id"`.
  - Every permission class is `read_only`/`write_draft`, and the Tool declares `idempotency: "execution_id"`.
  Everything else is unsafe. `external_side_effect`, `destructive`, and `sensitive_data` remain unsupported by the Tool Runtime support gate, whatever is declared.
- **Tool idempotency contract.** `ToolIdempotencySchema` is `"none"` (default) or `"execution_id"`. `execution_id` is a trusted implementation assertion: repeated invocations with the same AAO `toolExecutionId` resolve to one logical operation. `toolExecutionId` is the stable logical-operation key, derived from Run and Node identity. It is identical across in-process retries, process restarts, and recovery replays; the attempt number stays separate. AAO guarantees key stability, propagation, and replay rules. It cannot guarantee that an implementation or external provider honors the key.
- **Ordinary retries stay conservative.** `write_draft` is still never Runtime-retried after a known failure, even with `execution_id` idempotency. Crash replay is a separate, bounded mechanism.
- **Ambiguous operations.** A `STARTED` operation with no outcome is never read as "nothing happened". If recovery-safe and within the bound, the same attempt is replayed under the same attempt number and `toolExecutionId`, with `recoveryReplayCount` incremented compare-and-set before invocation. If unsafe, the host fails closed with `DURABILITY_UNSAFE_REPLAY`. If the bound is used up, it fails closed with `DURABILITY_RECOVERY_REPLAY_EXHAUSTED`. In both refusal cases nothing executes, nothing downstream runs, and durable truth is left untouched for future operator action. Only a durable cancellation request may still end such a Run.
- **Recovery replay is bounded.** `MAX_RECOVERY_REPLAYS = 1`: a single crash-replay of one attempt, then fail closed. It is a separate counter from `maxAttempts`, so a crash/restart loop cannot replay forever.
- **Durable retry accounting.** Recorded attempt failures are replayed through the same retry decision on resume. The next actual attempt is `recorded + 1`. `maxAttempts` remains one logical Node-execution budget that a restart never resets. A recorded final failure (non-retryable or exhausted) is committed without new attempts. A crash replay reuses its attempt number, so it never becomes a fresh logical operation or consumes retry budget. Changing a Node's reliability policy so that recorded attempts contradict it is `INVALID_RECOVERY_DIRECTIVE`.
- **Resume states.** `RUNNING` (current Node `READY`) continues through the single loop. `WAITING_FOR_APPROVAL` stays waiting until its durable Approval is resolved, which is a valid durable state and not a failure. `COMPLETED`, `FAILED`, and `CANCELLED` return their persisted outcome and evidence with zero executor calls. Resume never calls `createRunRecord`: Run identity and `createdAt` are preserved. A resumed process's clock is floored at the persisted `run.updatedAt`, so lifecycle time never moves backwards across restarts.
- **Durable Approvals.** `@aao/approval` defines an `ApprovalRepository` port (`get`, `create`, `compareAndSetResolution`). It ships `createInMemoryApprovalRepository` (the default, unchanged nondurable behavior), and `@aao/durability` implements a file repository. Resolution is atomic `pending → terminal` compare-and-set, so concurrent approve and reject can never both win. Exact request replay — the same id, run, node, fingerprint, and request metadata — returns the stored record, even when it is already resolved. It is never reopened or duplicated, which makes the Approval Node crash-safe. Any other request under that id is `APPROVAL_REQUEST_MISMATCH`.
- **Durable continuation revalidates.** Before an approved record is consumed — in any process — four checks run:
  - The plan fingerprint must match.
  - The current approval subject fingerprint must equal the stored request fingerprint (`APPROVAL_REQUEST_MISMATCH`).
  - Current Governance must still allow the requester the stored permission classes (`APPROVAL_REQUESTER_NOT_AUTHORIZED`).
  - The resolver must still be a registered human in a required role, under the self-approval rule (`APPROVAL_RESOLVER_NOT_ELIGIBLE`).
  A revoked approval leaves the Run waiting. Persisted roles, permissions, or approval evidence never grant authority; live Governance wins.
- **Safe-boundary cancellation.** A host persists an idempotent cancellation request. At the next safe boundary — before a Node would begin, or on resume of a waiting Run — the Run becomes `CANCELLED` and its `READY` Node (or waiting Approval Node) becomes `CANCELLED`. A terminal checkpoint is persisted, and a pending Approval is cancelled. No Node begins afterward. Cancellation does not interrupt a running attempt; cooperative `AbortSignal` stays best-effort. Cancellation stops future work; it does not reverse history, and there is no compensation framework.
- **Duplicate start.** Executing an existing `runId` returns `DURABLE_RUN_ALREADY_EXISTS` before any executor runs. Atomic Run creation with checkpoint 0 makes a racing duplicate fail before its first attempt.
- **Determinism.** Recovery decisions depend only on the checkpoint, the operation records, the plan, the registry metadata, the reliability policy, and approval state. There is no timestamp-based branching and no random decision.
- **No exactly-once claim.** AAO prevents replay of durably recorded completed operations and supports idempotent replay for operations explicitly designed for it. A remote success followed by a local crash before confirmation remains possible; idempotency manages that ambiguity and does not erase it.
- **Explicitly deferred:** `external_side_effect`, `destructive`, and `sensitive_data` stay unsupported. Durability is a prerequisite for them, not an enablement. Also deferred: queues, schedulers, worker pools, and distributed or multi-host execution; operator recovery tooling for refused ambiguous operations; compensation; tracing (Sprint 15); long-term memory; and Control Center UI.

## Consequences

An AAO process can disappear, and a new process can continue the workflow from durable execution truth. It does not rerun completed work or blindly repeat an operation whose outcome is unknown. The non-durable Runtime, in-memory Approval Engine, and every Sprint 0–13 behavior remain available. Per-attempt write-ahead records cost one extra small fsync'd file write per attempt and per boundary. That cost is acceptable for local-first execution, and a different store can change it behind the same port.
