# ADR-010: Managed Runtime State and Lifecycle

Status: accepted

## Context

Sprint 4 (ADR-009) produced a deterministic execution *function*: `executeWorkflow` ran a `CompiledWorkflowPlan` end to end and returned a single `{ ok, run | failure }` value, but nothing in the repository maintained an authoritative Run record, tracked per-Node status, or captured execution state at a point in time. There was no single place to answer "what Run is this, what lifecycle state is it in, which Nodes succeeded, and what does its state look like right now" without reconstructing the answer from a completed result. `RunRecord`, `RunStatus`, `NodeStatus`, and `StateSnapshot` already existed as canonical contracts (`@aao/contracts`, Sprint 2) and a frozen lifecycle (`docs/architecture/runtime-lifecycle.md`), but nothing implemented them. Before AAO can support persistence, interruption recovery, approvals, retries, or tracing, it needs a trustworthy, single-source-of-truth representation of "what state is this execution in right now" — without implementing any of those future systems yet.

## Decision

- `@aao/runtime` remains the single package for this work — no new `lifecycle`, `state`, or `snapshot` package. Node Registry, preflight, execution engine, Run lifecycle, Node lifecycle, state management, and snapshot capture all live inside `@aao/runtime`, matching the "smallest reliable architecture first" pattern ADR-009 established.
- `RunRecord` (`@aao/contracts`) becomes the sole authoritative source of Run lifecycle truth. The Runtime's public result (`WorkflowExecutionResult`) no longer carries a separate `run.status` field that could drift from it — Sprint 4's `RuntimeRunResult` is removed and replaced by `RuntimeExecutionState.run`, matching ADR-006/AGENTS.md's "one canonical implementation and contract per concept" rule.
- A Run Lifecycle Manager (`run-lifecycle.ts`) enforces the frozen legal transitions from `docs/architecture/runtime-lifecycle.md` (`isLegalRunTransition`, `transitionRunRecord`) purely and deterministically: `createdAt` is preserved, `updatedAt` always comes from an injected clock, and every transition is immutable. Terminal statuses (`COMPLETED`, `FAILED`, `CANCELLED`) reject every outgoing transition. An illegal transition throws (`IllegalRunTransitionError`) — a Runtime-internal invariant violation, never a `RuntimeFailure` value.
- A Node Lifecycle Manager (`node-lifecycle.ts`) maintains a `NodeStatusMap` (`Record<NodeId, NodeStatus>`) for every plan Node. Runtime V1 implements exactly one supported walk — `PENDING -> READY -> RUNNING -> SUCCEEDED | FAILED` — and legality-checks every transition (`isLegalNodeTransition`, `transitionNodeStatus`). The canonical `WAITING`/`SKIPPED`/`CANCELLED` statuses exist in the contract but have no Runtime V1 behavior; nothing in this package produces them yet.
- Managed execution follows `CREATED -> VALIDATING -> QUEUED -> RUNNING -> COMPLETED | FAILED`. `QUEUED` is an intentionally transient in-process status — validation passed and the local Runtime immediately claims execution capacity — not a durable queue, worker, or broker; no such infrastructure is introduced. A request that cannot be trusted enough to construct a `RunRecord` at all (malformed plan/state/registry/options) is rejected by `validateRuntimeInput` before any Run exists (`INVALID_RUNTIME_INPUT`, no `execution`/`latestSnapshot`). Once a `RunRecord` exists, every later failure (preflight, Node execution, a malformed result, the step ceiling) is an authoritative `RunRecord.status = FAILED` with a safe snapshot, never a silent rejection.
- `RunRecord.currentNodeId` is the single execution cursor — no second "current node" field is introduced. While `RUNNING` it identifies the Node currently eligible to execute (`READY`) or executing (`RUNNING`); it is always cleared (`setCurrentNodeId(run, undefined)`) on every transition into a terminal status, so a terminal Run's cursor is never ambiguous.
- An explicit `RuntimeClock` boundary (`clock.ts`) replaces every direct `new Date()`/`Date.now()` call in Runtime lifecycle code. `createSystemClock()` is the production implementation; `RuntimeOptions.clock` lets a caller (chiefly tests) inject a deterministic one. Every timestamp minted this way is validated against the canonical ISO timestamp contract before it enters a `RunRecord` or `StateSnapshot`.
- State/reducer semantics are unchanged from Sprint 4 (shallow top-level patch merge; revision increments by exactly one only when a patch is actually accepted) — no reducer registry, deep merge, delete operator, or CRDT is introduced. `execution step` and `state revision` remain distinct counters that can diverge (a no-op Node advances step but not revision).
- `captureStateSnapshot(state, capturedAt)` (`state.ts`) builds a canonical `StateSnapshot` (`@aao/contracts`) from a `RunState` at an explicit, clock-sourced timestamp.
- A new Runtime-owned artifact, `RuntimeExecutionSnapshot` (`execution-snapshot.ts`), captures a *safe* execution boundary: Run lifecycle (`RunRecord`) + a canonical `StateSnapshot` + Node lifecycle (`NodeStatusMap`) + execution `step`. `captureExecutionSnapshot` refuses (throws) to capture a snapshot while any Node is `RUNNING` — a snapshot can only represent a moment between Nodes, never mid-execution. The Runtime retains only the single `latestSnapshot` at any time, updated at each safe boundary; it does not accumulate a full in-memory snapshot archive.
- `RuntimeExecutionSnapshot` is explicitly **not** a durable checkpoint and is distinct from the canonical `CheckpointRecord` (`@aao/contracts`), which represents recovery *state data*, not proof that durable recovery exists. No workflow resume, persistence, or replay is implemented this sprint — `validateSnapshotAgainstPlan` exists only to prove a snapshot is contextually compatible with a specific `CompiledWorkflowPlan` (workflow identity, cursor resolution, safe-boundary coherence per `RunStatus`), groundwork for a future resume/handoff feature that is deliberately not built yet.
- `NodeExecutionRecord` (execution history) now represents `"SUCCEEDED" | "FAILED"` (previously `"SUCCEEDED"` only), so a failed Node's execution is evidenced the same way a successful one is (`stateRevisionBefore === stateRevisionAfter` always holds for a `FAILED` record, since no patch is ever applied from a Node that threw or returned an invalid result). This remains deliberately minimal execution evidence, not the future canonical AAO Trace — no timestamps, latency, cost, or trace ids are added.
- The canonical-JSON edge-fingerprint helper duplicated between `@aao/workflow-dsl` (duplicate-edge detection) and `@aao/runtime` (preflight's outgoing/incoming edge-set cross-check, which previously used raw, non-canonical `JSON.stringify`) is promoted to `@aao/contracts` (`canonicalJsonStringify`, `json.ts`) — both packages already depend on `@aao/contracts`, so this avoids both a private cross-package import and duplicated fingerprint logic. `@aao/workflow-dsl`'s own `canonical-json.ts` becomes a thin re-export so its existing local import and test keep working unchanged.
- No cancellation, approval, or retry *execution* is implemented — `WAITING_FOR_APPROVAL` and `RETRYING` remain reachable only as contract values, never as Runtime V1 behavior. No persistence, queue infrastructure, LangGraph, AI/model/tool/agent execution, or external side effect is introduced.

## Consequences

- `packages/runtime` gains `clock.ts`, `run-lifecycle.ts`, `node-lifecycle.ts`, and `execution-snapshot.ts`, plus `captureStateSnapshot` in `state.ts`; `engine.ts` is substantially rewritten to build and thread `RuntimeExecutionState` through every safe boundary rather than only returning a final result. `WorkflowExecutionResult` changes shape (`execution`/`latestSnapshot` replace the old `run` field) — this is a breaking change to Runtime V1's public API, accepted deliberately per AGENTS.md/ADR-009's "correctness over preserving an accidental V1 API" stance for this pre-V1 project; every Runtime test, the compiler integration test, and the deterministic example were updated accordingly, and no compatibility wrapper was added.
- Authoritative Node-lifecycle tracking surfaced a real corrupted-plan gap Sprint 4's defensive checks did not cover: a manually corrupted plan that routes back to an already-`SUCCEEDED` Node (impossible from a real compiled plan, since Workflow Compiler V1 rejects cycles) is now caught deterministically as `RUNTIME_PREFLIGHT_FAILED` the moment re-entry is attempted, rather than only being caught indirectly once execution happened to exceed `maxSteps`. The engine's own re-entry guard converts this into a graceful `RuntimeFailure`, matching every other "corrupted plan discovered mid-execution" check already in `engine.ts`, rather than letting `IllegalNodeTransitionError` escape as an uncaught exception.
- `packages/runtime`'s test suite grows substantially: `clock.test.ts`, `run-lifecycle.test.ts`, `node-lifecycle.test.ts`, `execution-snapshot.test.ts`, and `managed-execution.test.ts` are new; `state.test.ts` gains `captureStateSnapshot` coverage; `preflight.test.ts` gains the canonical-JSON-fingerprint carryover test; `integration-compiler.test.ts` gains a real YAML → compiler → managed-Runtime failure end-to-end test alongside the existing success path; `engine-safety.test.ts`'s `MAX_STEPS_EXCEEDED` test is rebuilt around a genuinely long valid plan with a caller-configured low ceiling (its previous cyclic-corrupted-plan premise now hits the new re-entry guard first, which is now covered by its own dedicated test).
- `apps/control-plane` and `apps/worker` remain unconnected to the Runtime, unchanged from ADR-009 — there is still no durable Run store, scheduler, or job-ownership protocol to justify wiring managed execution into the Worker operationally.
- Sprint 6 (Model Abstraction & Capability Routing) can now assume a trustworthy, inspectable managed execution state exists at every safe boundary, without needing to re-litigate Run/Node lifecycle, snapshot, or clock design — and any future persistence, resume, approval, or retry implementation has a concrete `RuntimeExecutionSnapshot` shape to build against rather than inventing one from scratch.
