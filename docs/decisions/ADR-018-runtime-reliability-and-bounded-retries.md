# ADR-018: Runtime reliability and bounded retries

Status: accepted

## Context

Sprints 5–12 executed each Node exactly once. A transient dependency failure failed the Run, and there was no way to bound a hung attempt. Adding retries carelessly creates duplicate side effects, retries that "create" missing authority, and timed-out work that later overwrites state. Sprint 13 adds a reliability layer without a second execution engine.

## Decision

- **The Runtime owns infrastructure retry.** `@aao/runtime` contains one Reliability Controller (`reliability.ts`). The canonical `runLoop` calls it once per Node execution; it returns at most one accepted outcome, and only `runLoop` applies state, transitions lifecycle, and routes. Tool Runtime, the MCP connector, the Model Runtime, and the Agent Runtime contain no retry loops, sleeps, or races. Agent reasoning iteration (ADR-012) is not failure retry.
- **Default is one attempt.** Without a policy every Node has `maxAttempts = 1`, so execution cardinality is unchanged from Sprint 12.
- **Policy is trusted, schema-validated, and hard-capped.** `ReliabilityPolicySchema` (`@aao/contracts`) is a strict JSON-safe `{ maxAttempts, attemptTimeoutMs?, retryDelayMs? }` with `RELIABILITY_LIMITS`: `1 ≤ maxAttempts ≤ 3`, `1 ≤ attemptTimeoutMs ≤ 600000`, `0 ≤ retryDelayMs ≤ 60000`. The host supplies policies only through `RuntimeOptions.reliability.policiesByNodeId`; they are validated against the plan before a Run exists (`INVALID_RUNTIME_INPUT` otherwise) and frozen. Workflow source, node config, workflow state, model/Agent/Tool output, MCP metadata, and memory have no channel to it. A fixed delay only: no exponential backoff, jitter, adaptive windows, or provider retry headers.
- **A retry requires all three:** the policy permits another attempt; the failure's structured category is retryable; the executor declared the node retry-safe.
- **Retry safety is explicit and defaults to unsafe.** `NodeExecutor.retrySafety?(node)` is trusted, deterministic metadata; absent, thrown, or anything but `"safe"` means unsafe. The Tool Node answers with the registered Tool's `retrySafety`, which defaults to `"unsafe"` and may be `"safe"` only when every permission class is `read_only`. `write_draft` Tools are never Runtime-retried in Sprint 13: a draft write can duplicate artifacts and no idempotency contract exists yet. Model and Agent executors declare nothing and are therefore not retried; Agent Nodes may orchestrate several model calls and future Tool use, so safe classification cannot be guaranteed.
- **One failure taxonomy, fail closed.** `FailureCategorySchema`: `VALIDATION`, `AUTHORIZATION`, `POLICY`, `APPROVAL`, `TIMEOUT`, `TRANSIENT_DEPENDENCY`, `RATE_LIMIT`, `EXECUTION`, `INTERNAL`. Only `TIMEOUT`, `TRANSIENT_DEPENDENCY`, and `RATE_LIMIT` are retryable. Executors classify their own expected failures through an optional `category` on the bounded `{ namespace, code }` executor failure; an unclassified failure is `EXECUTION`, a thrown value is `INTERNAL`, and a malformed result or patch is `VALIDATION`. No decision ever reads an error message or thrown value.
- **Tool classification.** A handler may return `{ ok: false, code, retryable: true }` — its only way to declare an explicitly transient dependency failure — surfaced as `ToolFailure.handlerFailureRetryable`. The Tool Node maps authorization failures to `AUTHORIZATION`, the support gate to `POLICY`, request/schema/result failures to `VALIDATION`, flagged handler failures to `TRANSIENT_DEPENDENCY`, and everything else to `EXECUTION`. The MCP connector never sets the flag, so `MCP_CALL_FAILED` and every other MCP code is non-retryable.
- **Failed attempts never commit.** Each attempt receives a fresh defensive clone of the same authoritative state. A patch is applied exactly once, from the single accepted successful attempt. Failed and timed-out attempts never change state or `RunState.revision`.
- **Per-attempt timeout with best-effort cooperative cancellation.** When `attemptTimeoutMs` is set, the attempt races an injected `RuntimeSleeper`. On timeout the Runtime aborts the attempt's `AbortSignal` (passed in `NodeExecutionContext.signal` and forwarded by the Tool Node to the handler) and classifies `TIMEOUT`. JavaScript cannot stop arbitrary async work, so cancellation is cooperative only.
- **Late results are ignored structurally.** Only the race winner is returned to the commit path. A timed-out attempt that settles later resolves into a value nothing reads: no patch, no Node transition, no output.
- **Retries stay inside one Node lifecycle.** The Node remains `RUNNING` and the Run remains `RUNNING` across attempts. No `READY → RUNNING` bounce occurs, no clock reading or snapshot is taken between attempts, and the canonical `RETRYING` Run status stays unused: in-process retries have no external coordination need, and using it would create a second truth beside attempt metadata. `RETRYING` stays reserved for a future durable, scheduled retry.
- **Bounded evidence, not tracing.** Every `NodeExecutionRecord` carries `attemptCount` and, when attempts failed, `attemptFailures: [{ attempt, category, causeCode }]`. Every Node execution failure carries `category`, `retryable` (the failure's nature), `attempt`, and `maxAttempts`. Exhaustion is `NODE_RETRY_EXHAUSTED` with the last bounded `causeCode`; a non-retried timeout is `NODE_ATTEMPT_TIMEOUT`. Redaction rules are unchanged.
- **Approval waits are not failures.** A wait result ends the attempt sequence as a nonterminal outcome. A multi-attempt policy on an Approval Node is rejected as invalid configuration. Continuation invokes no executor and records `attemptCount: 1`. Approval rejection, expiry, and cancellation surface with category `APPROVAL` and are never retried.
- **Denials are never retried.** Governance DENY and Authorization DENY (including Agent ceiling failures) reach the Runtime as `AUTHORIZATION`. Unsupported permission classes still fail preflight before any Node runs, so a retry policy can never make an `external_side_effect`, `destructive`, or `sensitive_data` handler execute.
- **Execution identity.** The deterministic `toolExecutionId` names the logical Node execution and stays the same on every attempt. The attempt dimension lives in Runtime accounting (`NodeExecutionContext.attempt`, history), not in the id. This keeps a stable key for Sprint 14 idempotency design.

## Consequences and limits

- Safe snapshot boundaries are unchanged: after accepted Node success, at a workflow waitpoint, and at terminal failure/cancellation. A snapshot is never taken while an attempt runs, and never implies that a timed-out but still physically running attempt can be resumed. Snapshot `schemaVersion` stays 2: attempt metadata lives in execution history and failures, and at every safe boundary each attempt sequence is complete.
- Reliability is process-local. A crash between attempts loses the attempt count. Durable Run persistence, checkpoints, crash recovery, durable retry accounting, idempotency, and replay protection belong to Sprint 14.
- Retry safety ≠ idempotency. Sprint 13 only permits bounded in-process retries of read-only operations and of trusted executors that declare safety. It provides no exactly-once guarantee.
- `external_side_effect`, `destructive`, and `sensitive_data` remain unsupported. No side effect is ever retried.
- Tracing, spans, metrics, and audit belong to Sprints 15–16. No circuit breaker, distributed queue, provider reconnect, or MCP retry exists.
- A future Workflow DSL or framework surface (`defineWorkflow({ reliability })`) and Capability Pack recommendations must pass through the same schema and hard caps and cannot override retry safety.
