# AAO Evals

Version-controlled evaluation assets for the AAO Evaluation Runtime (`@aao/evaluation`; [ADR-022](../docs/decisions/ADR-022-evaluation-runtime-and-portable-verification.md), [architecture](../docs/architecture/evaluation-runtime.md)). There is no database: everything here is plain YAML/JSON, reviewed like code.

```text
evals/
├── definitions/runtime-foundation.v1.yaml   EvalDefinition v2 — what is judged, by which trusted grader
├── datasets/runtime-foundation.v1.yaml      EvalDataset v1 — stable cases pointing at evidence
└── fixtures/*.json                          EvalEvidenceBundle — recorded canonical AAO evidence
```

## Definitions, datasets, and evidence stay separate

- A **definition** states a criterion: a `targetType`, an exact `graderRef { id, version }`, and JSON config. It never contains evidence.
- A **dataset** lists **cases**. Each case is `evalRef + mode + evidenceRef + expected`. A case references its evidence; it never embeds a Run or Trace. The same case can later point at a live Run, a recorded regression Trace, or another adapter's Trace.
- A **fixture** is one `EvalEvidenceBundle`. It can hold canonical Trace events, Runtime execution state, Trace-derived `RunMetrics`, an Audit stream, and, for semantic judges only, an explicit subject.

## Versioning

- Definitions, datasets, and graders are versioned independently. An `EvalResult` records all three (`evalRef`, `graderRef`, `datasetRef` + `caseId`), so results stay comparable.
- Changing any material criterion requires a new definition `version`. Examples are a different Tool, threshold, rubric, pass threshold, or sequence mode. Old results are never reinterpreted under new criteria.
- Changing the cases a dataset contains requires a new dataset `version`.
- A grader whose semantics change ships as a new grader version and is registered alongside the old one.

## Case ids

Case ids are stable, human-assigned regression identities, never autogenerated: `<area>.<behavior>.<NNN>`, for example:

- `tool.forbidden-after-rejection.001`
- `authorization.denied-no-handler.001`
- `retry.authorization-not-retried.001`

Never renumber or reuse an id. Add `.002` for a new variant of the same behavior.

## Expected and forbidden behavior

Every case states the verdict it exists to prove:

| `expected.status` | Meaning | Example |
| --- | --- | --- |
| `passed` | Desired behavior | Approval rejected, Run failed, downstream Tool calls = 0 |
| `failed` | Forbidden behavior is detected | Tool started after a rejected Approval; retry after an Authorization denial |
| `error` (+ `errorCode`) | Untrustworthy or insufficient evidence must never pass | Corrupt Trace; cost `unavailable`; no rejection occurred, so "no Tool after rejection" is untestable |

## OFFLINE vs RUNTIME

Committed fixtures are `origin: recorded` and run in `OFFLINE` mode. `RUNTIME` mode is for evidence from a real, current Run (`origin: live_run`) that the host hands over after the Runtime returned. Most definitions support both modes, and the same grader judges both.

## Evidence references

`evidenceRef` is an opaque `scheme://path` string (for example `fixture://flagship-approved`). The Evaluation Runtime never opens it. A host maps references to evidence through an injected `EvidenceResolver`: tests and the compiled smoke map `fixture://<name>` to `evals/fixtures/<name>.json` explicitly. Results cite evidence by reference (`trace://<run>/event/<seq>`, `execution://<run>/state-revision/<n>`, …), never by copying it.

## Rules

- **No secrets.** Fixtures contain only fake, clearly labelled strings such as `FIXTURE_STATE_SECRET_DO_NOT_PERSIST`. The privacy suite proves they never reach an `EvalResult`.
- **No code.** Definitions and datasets cannot carry `modulePath`, `javascript`, `functionBody`, `shellCommand`, `script`, `require`, `import`, `exec`, or similar keys at any depth. YAML with unknown tags (e.g. `!!js/function`) is rejected. Graders are trusted code registered by the host.
- **Canonical semantics only.** Criteria use AAO event types, `ToolRef`s, Run status, failure categories, state paths, and `RunMetrics`, never framework or provider constructs.
- **Bounded.** A dataset holds at most 200 cases, a config at most 16 KiB, and a source file at most 1 MiB.

## Regenerating fixtures

Fixtures are rebuilt deterministically on every `pnpm test` (`packages/evaluation/test/foundation-fixtures.test.ts`) and compared with the committed files:

- Positive evidence comes from real AAO Runs (Runtime, Approval Engine, Tool Runtime, Authorization, Trace and Audit recorders).
- Negative evidence is synthetic but recorder-validated: valid Traces of undesired behavior that the Runtime itself prevents.

After an intentional change, update the fixtures with `pnpm vitest run packages/evaluation/test/foundation-fixtures.test.ts -u` and review the diff.

## Not here (Sprint 18+)

This directory contains no result history, pass-rate trends, baselines, CI gates, or automatic regression creation.
